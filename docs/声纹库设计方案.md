# 声纹库设计方案

> 状态：二期规划 | 日期：2026-07-28

## 一、现状问题

当前 step6 Demo 使用 SpeakerClusterer 做**单文件内聚类**：每上传一段音频，在文件内部做 embedding + 聚类，生成 `speaker_0`、`speaker_1` 等临时标签。

**两个问题**：

1. **跨文件 ID 不关联**：同一管制员在两段录音里被分配不同 ID，系统不知道是同一个人
2. **个体基线无法积累**：SpeakerBaseline 依靠 speaker_id 积累历史数据。跨文件 ID 不匹配 → 每次都是冷启动 → 个体基线永远不会达到稳定态（>100 段）

## 二、目标

建立**持久化声纹库**，实现：

- 同一个人的不同录音自动关联
- 个体基线真正积累（冷启动 → 过渡 → 稳定）
- 支持登记已知管制员（身份绑定）

## 三、技术方案

### 3.1 架构流程

```
音频上传 → VAD 分段 → 降噪
                        ↓
                ERes2NetV2 提取 192d embedding
                        ↓
           ┌─────────────────────────┐
           │  声纹库 (voiceprint_db)  │
           │  ┌───────┬─────────────┐│
           │  │ 质心  │ 身份标签     ││
           │  ├───────┼─────────────┤│
           │  │ vec_0 │ controller_A ││
           │  │ vec_1 │ controller_B ││
           │  │ ...   │ ...          ││
           │  └───────┴─────────────┘│
           └─────────────────────────┘
                        ↓
            余弦匹配 → 已知说话人？→ 分配 persistent_id
                        ↓ 新说话人
            注册新质心 + 自动分配 ID
                        ↓
              个体基线按 persistent_id 累积
```

### 3.2 匹配策略：逐段直接匹配

**核心改进**：跳过文件内聚类，每段 embedding 直接与声纹库匹配。

| 方案 | 原方案（聚类→匹配） | 改进方案（逐段匹配） |
|------|---------------------|---------------------|
| 流程 | VAD 分段 → 文件内聚类 → 取质心 → 匹配 DB | VAD 分段 → 逐段 embedding → 直接匹配 DB |
| 误差传播 | 聚类错误（合并/拆分）会污染质心，DB 匹配继承错误 | 每段独立判定，不存在中间误差传播 |
| 粒度 | 每个 cluster 一个 ID（粗） | 每段一个 ID（细），同人的段自然归到同一 ID |
| 代价 | 需要 get_cluster_embeddings 改造 | 无需改动 cluster.py |

同一文件内同一个人的多段 embedding 会自然匹配到同一个 persist_id，不需要先聚类再匹配。

### 3.3 自适应匹配阈值

固定阈值 0.55 在不同场景下表现差异大。改为根据说话人已积累样本数自适应：

| 说话人阶段 | n_samples | 阈值 | 理由 |
|-----------|-----------|------|------|
| 冷启动 | 1-5 | 0.62 | 质心仅 1 条样本，噪声大，高阈值防误匹配 |
| 过渡期 | 6-30 | 0.58 | 质心逐渐稳定，适度放宽 |
| 稳定期 | >30 | 0.52 | 质心可靠，放宽阈值提高召回 |

同时引入**灰区**（阈值 - 0.05 ~ 阈值）：相似度落在灰区时标记 `uncertain`，不自动注册新说话人，保留两条候选 ID 供后续人工或更多数据判定。

### 3.4 说话人漂移处理

人的声音会随疲劳、健康状态、时间变化。处理策略：

- **活跃度判定**：`last_seen` 超过 30 天的说话人，匹配阈值临时提高 0.05（质心可能过时）
- **质心衰减**：长期未活跃的说话人（>90 天），在 summary 中标记 `stale`，提示管理员复核
- 不自动删除：仅在人工确认后删除

### 3.5 声纹库存储结构

文件：`output/voiceprint_db.json`

每个说话人记录：

| 字段 | 类型 | 说明 |
|------|------|------|
| `label` | string | 人工标签（如 `controller_张`）或自动标签 |
| `centroid` | float[192] | L2 归一化后的质心向量 |
| `n_samples` | int | 已积累的 embedding 样本数 |
| `first_seen` | ISO 8601 | 首次注册时间 |
| `last_seen` | ISO 8601 | 最近一次匹配时间 |
| `registered` | bool | 是否已人工登记 |
| `match_history` | float[] | 最近 50 次匹配的相似度（用于质量追踪） |

全局配置：`version`、`model`（embedding 模型 ID）、`base_threshold`（基础阈值，默认 0.55）。

### 3.6 质心更新

采用 EMA（指数移动平均）：
- alpha = min(0.1, 1/n)：早期样本权重高（快速建立质心），后期随 n 衰减（保持稳定）
- 每次更新后 L2 归一化
- 新匹配的相似度追加到 `match_history`（保留最近 50 条），用于分析匹配质量分布

### 3.7 写入策略

**批量延迟写入**：每次请求（可能包含多个文件）期间，所有匹配/注册操作在内存中完成。请求结束后一次性写入 JSON。

- 避免批量处理 30 段时 30 次全量 JSON 写入
- 如果进程崩溃，最多丢失最后一次请求的数据（可接受）

## 四、SpeakerBaseline 持久化

### 4.1 问题

当前方案说恢复全局 SpeakerBaseline，但未解决其自身持久化问题。进程重启后：
- 声纹库（JSON）还在
- SpeakerBaseline 的运行统计（sum_a, sum_sq_a, n）全丢 → 又回到冷启动

### 4.2 方案

SpeakerBaseline 与声纹库共享同一个 JSON 文件，或使用配套文件 `output/speaker_baseline.json`：

| 字段 | 说明 |
|------|------|
| `speakers` | 每个 persist_id 的运行统计：sum_a, sum_sq_a, n |
| `global` | 群体基线参数：mean, std |

- 启动时加载，与声纹库同步
- 请求结束时与声纹库一起批量写入
- 删除说话人时同步删除其基线统计

## 五、Demo 集成方案

### 5.1 改动点

1. **模块级加载**：启动时加载 VoiceprintDB + SpeakerBaseline（均为持久化实例）
2. **逐段匹配**：`_process_single_file` 中，每段 embedding 提取后直接调用 `voiceprint_db.match_and_update()`，跳过文件内聚类
3. **持久 ID 贯穿**：匹配返回的 `persist_*` ID 直接用于 SpeakerBaseline、状态判定、DataFrame 输出
4. **请求结束批量写入**：一次分析完成后，voiceprint_db.save() + speaker_baseline.save() 各调一次

### 5.2 流程对比

```
当前（会话级）:
  VAD → openSMILE → XGBoost → 文件内聚类(speaker_0/1) → SpeakerBaseline(per-request)

改后（跨请求持久）:
  VAD → openSMILE → XGBoost
            ↓
    ERes2NetV2 逐段提取 embedding
            ↓
    VoiceprintDB.match_and_update(emb) → persist_003
            ↓
    SpeakerBaseline(全局持久).normalize(persist_003, a, e)
            ↓
    [请求结束] → voiceprint_db.save() + speaker_baseline.save()
```

### 5.3 文件变更清单

| 操作 | 文件 | 说明 |
|------|------|------|
| 新建 | `step0_voiceprint/db.py` | VoiceprintDB 核心类 |
| 修改 | `step0_voiceprint/__init__.py` | 导出 VoiceprintDB |
| 修改 | `step6_demo/app.py` | 集成声纹库匹配 + 恢复全局 Baseline |
| 新建 | `output/voiceprint_db.json` | 运行时自动生成 |
| 新建 | `output/speaker_baseline.json` | 运行时自动生成 |

注意：`step0_voiceprint/cluster.py` **无需改动**（逐段匹配方案不再需要聚类质心）。

### 5.4 UI 管理 Tab

新增「声纹库」Tab：

- 表格列：ID、标签、样本数、基线阶段（cold/warm/stale）、平均匹配相似度、首次/最后活跃时间
- 重命名功能
- 合并功能（质心取加权平均，match_history 合并）
- 删除功能（同步删除声纹库记录 + SpeakerBaseline 统计）
- 合规提示：告知声纹属于敏感个人信息

## 六、实施顺序与检查点

| # | 步骤 | 检查点 |
|---|------|--------|
| 1 | 创建 `db.py`：VoiceprintDB 核心 + 单元测试 | 匹配/注册/合并/持久化/自适应阈值 全绿 |
| 2 | SpeakerBaseline 持久化：save/load + 与声纹库联动 | 进程重启后基线统计不丢失 |
| 3 | 改造 `app.py`：逐段匹配 → 持久 ID → 全局 Baseline → 批量写入 | REC-1 连续两次上传，speaker ID 一致 |
| 4 | 基线累积验证：同一说话人逐段上传，观察 confidence 从 low → medium → high | 30 段后进入过渡期 |
| 5 | 匹配质量分析：检查 match_history 分布，调优自适应阈值参数 | 误匹配率 < 5% |
| 6 | UI 管理 Tab | 重命名/合并/删除 可操作且持久化 |
| 7 | 回归测试：4 段 REC 批量分析 | 判定结果不退化 |

## 七、异常处理

| 场景 | 处理 |
|------|------|
| 声纹库文件不存在 | 创建空库，全部自动注册 |
| JSON 损坏 | 警告 + 备份为 .bak + 重建空库 |
| 零向量片段 (<0.3s) | 跳过匹配，标记 confidence=low |
| 灰区匹配（相似度在阈值附近） | 标记 uncertain，不自动注册新说话人 |
| 进程崩溃 | 最多丢失最后一次请求的数据，重启后从 JSON 恢复 |

## 八、回滚方案

误匹配严重时，直接删除 `output/voiceprint_db.json` 和 `output/speaker_baseline.json` → 系统回到冷启动状态（等同于当前会话级行为）。模型推理和特征提取完全不受影响。

## 九、风险与约束

1. **匹配阈值需实测调优**：自适应阈值参数（冷启动 0.62、稳定 0.52）是经验估计，需用真实数据验证
2. **信道差异**：不同录音设备/环境的 embedding 可能有偏移。考虑按信道分组或使用信道补偿（三期）
3. **声纹合规**：根据《个人信息保护法》，声纹属于敏感个人信息。Demo 界面需告知用户并提供删除入口
4. **冷启动期**：声纹库建立初期大部分是新说话人，价值随使用积累逐步提升
5. **并发限制**：JSON 文件不支持并发写入，Demo 单用户使用无问题，多用户场景需加文件锁或迁移到 SQLite
